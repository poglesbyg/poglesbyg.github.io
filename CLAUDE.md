## Commands

The Pages workflow (`.github/workflows/pages.yml`) builds with `actions/jekyll-build-pages`,
which runs the `github-pages` gem: **Jekyll 3.10**, not 4. The faithful local build is
that same container (Docker via OrbStack on this machine; system Ruby is 2.6 and too old
for Bundler):

```bash
docker run --rm -v "$PWD":/github/workspace \
  -e INPUT_SOURCE=. -e INPUT_DESTINATION=./_site -e GITHUB_WORKSPACE=/github/workspace \
  ghcr.io/actions/jekyll-build-pages:v1.0.13
python3 -m http.server -d _site 4000
```

`python3 -m http.server` doesn't map `/projects` to `projects.html` the way GitHub Pages
does, so open the `.html` paths when previewing locally.

The Gemfile still pins Jekyll 4.3.2, which is not what deploys. The workflow ignores it
(and warns about the mismatch on every run). Don't treat `bundle exec jekyll serve` output
as a preview of production.

Pushing to `main` deploys.

## Architecture

A small Jekyll site: four pages, posts, one stylesheet, one short script. No frameworks,
no icon fonts, no service worker.

| File | Purpose |
|------|---------|
| `_config.yml` | Site title/description, `jekyll-seo-tag` settings, post permalinks, the default share image |
| `_layouts/default.html` | `<head>` (`{% seo %}` + `{% feed_meta %}`), header nav, one-line footer |
| `_layouts/post.html` | Title, date, `.prose` body, previous/next links |
| `assets/css/main.css` | All styles. Tokens at the top. |
| `assets/js/main.js` | The theme toggle and nothing else |
| `service-worker.js` | A self-unregistering stub. See below. |

- Head meta, Open Graph, Twitter card, canonical URLs, and JSON-LD all come from
  `jekyll-seo-tag`. Don't hand-write them back into the layout. Posts get
  `og:type=article` automatically.
- The sitemap is generated by `jekyll-sitemap`. Don't add a static `sitemap.xml`; it would
  shadow the plugin and go stale with every post.
- `projects.md`, `blog.md`, and `contact.md` set `permalink: /projects` (etc.) so the
  canonical URL, the sitemap, and the nav links all agree. Jekyll still writes
  `projects.html`, so old `.html` links keep working.

### Design

- One column (`--measure: 42rem`). Header, main, and footer share it, so every element
  starts at the same left edge. Keep new sections on that column.
- Headings are a system monospace stack; body is DM Sans (the only web font). The
  monospace headings are deliberate.
- One accent, the taupe: `#a89968` in dark mode, darkened to `#7b6f47` in light mode
  because the original was 2.7:1 on the light background. Every text color is commented
  with its contrast ratio; keep new colors at 4.5:1 or above.
- Theme: with nothing saved, CSS follows `prefers-color-scheme` on its own. The footer
  toggle adds a `light` or `dark` class to `<html>` and saves it to `localStorage`; an
  inline script in `<head>` reapplies it before first paint.
- `.list` rows are a two-column grid: a `<time>` stays pinned top-right while the title
  wraps, and a `<span class="meta">` takes a full line underneath.

### The service worker stub

The site used to register a service worker that cached CSS and JS cache-first, which
served stale assets to returning visitors. Deleting `service-worker.js` wouldn't remove it
from browsers that already had it, so the file is now a stub that clears all caches and
unregisters itself when those browsers check for an update. Nothing registers it anymore.
It can be deleted once old registrations have cycled out (2027).

## Content guidelines

Pages: `index.md` (home), `projects.md`, `blog.md` (titled "Writing"), `contact.md`, and
`404.md`. `stillpoint/` holds the support and privacy pages for the Stillpoint Mac app.
They have their own stylesheet and are linked from the app; leave them alone unless asked.

The homepage is intro, then Writing (latest three posts, automatic), then Projects (three
picked by hand, linking to anchors on `/projects`), then Experience. Adding a post updates
the homepage, the Writing page, the feed, and the sitemap on its own.

Positioning: "Data scientist. I measure whether results survive a second check." That
through-line ties the posts and projects together; the USDA Forest Service role
(via Leading Solutions, LLC) and the UNC Chapel Hill clinical background are supporting
facts in the bio and Experience. Keep `_config.yml`'s `description` consistent with the
homepage lede.

Posts are long-form and numeric: one specific measured finding, tables for the numbers, a
section on how the numbers were produced, and an explicit "what this is not". Every post
needs a `description` in its front matter. It's what the Writing page, the feed, and link
previews show. Match the voice of the existing posts: plain, few em dashes, no aphoristic
closers.

## Skill routing

When the user's request matches an available skill, ALWAYS invoke it using the Skill
tool as your FIRST action. Do NOT answer directly, do NOT use other tools first.
The skill has specialized workflows that produce better results than ad-hoc answers.

- Product ideas, "is this worth building", brainstorming → invoke office-hours
- Bugs, errors, "why is this broken", 500 errors → invoke investigate
- Ship, deploy, push, create PR → invoke ship
- QA, test the site, find bugs → invoke qa
- Code review, check my diff → invoke review
- Update docs after shipping → invoke document-release
- Weekly retro → invoke retro
- Design system, brand → invoke design-consultation
- Visual audit, design polish → invoke design-review
- Architecture review → invoke plan-eng-review
- Save progress, checkpoint, resume → invoke checkpoint
- Code quality, health check → invoke health
